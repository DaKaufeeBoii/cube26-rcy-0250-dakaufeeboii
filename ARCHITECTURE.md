## 1. System Architecture

The AI Recovery Manager is architected as an autonomous evidence-to-recovery intelligence engine designed around modular, decoupled components. It integrates multi-source operational telemetry with financial adjustment records to execute defensible, audit-proof dispute recovery.

## 2. Components Breakdown

### 2.1 Domain Models (`recovery_manager/models.py`)
Encapsulates strongly-typed schemas using Pydantic v2:
- **`FeeCharge`**: Normalized representation of ingested fee penalties (Charge ID, Shipment ID, Order ID, SKU, Unit ID, Fee Type, Reason, Amount, Currency, Date).
- **`ReimbursementRecord`**: Concessions, prior credits, and refunds already granted.
- **`OperationalEvidence`**: Upstream records generated by operational managers (`Receiving`, `Prep`, `Pack`, `Shipping`, `Returns`). Stores check types, status codes, telemetry metrics (`details`), and media references.
- **`EvidenceMatch`**: Quantified correlation between a charge and an operational record with relevance scoring and contradiction/support categorization.
- **`RecoveryResult`**: Individual assessment per charge (`CONTRADICTED`, `SUPPORTED`, `SILENT`, `UNCERTAIN`, `DUPLICATE`, `ALREADY_REIMBURSED`), claim status (`ACTIONABLE`, `NOT_SUPPORTED`, `INCONCLUSIVE`, `RESOLVED`), and potential claim amount.
- **`RecoveryDossier`**: Comprehensive audit dossier aggregating financial metrics, individual results, and compliance disclosures.

### 2.2 Ingestion & Parser Engine (`recovery_manager/parser.py`)
- Ingests raw JSON or CSV fee reports, past reimbursement reports, and multi-manager operational evidence records.
- Standardizes diverse column nomenclatures (e.g. mapping `FNSKU`, `Unit`, `ASIN` -> `sku`; `Reason`, `Description`, `Fee Type` -> `fee_type`).
- Dynamically resolves Manager types via semantic tagging.

### 2.3 Multi-Index Evidence Store (`recovery_manager/store.py`)
- Employs an in-memory multidimensional index providing $O(1)$ lookup across:
  - `by_shipment`: Index by shipment reference
  - `by_order`: Index by customer order identifier
  - `by_sku`: Index by product catalog identifier
  - `by_unit`: Index by item serial / tracking code
  - `by_charge_id`: Index for previously processed reimbursements
- Ensures candidate records from disparate departments are quickly aggregated for cross-manager analysis.

### 2.4 Autonomous Recovery Reasoning Engine (`recovery_manager/engine.py`)
- Executes the core 10-step protocol.
- Contains the semantic mapping dictionary linking fee types to relevant operational checks and managers:
  - *Packaging Defect* -> Prep / Pack / Receiving (`packaging`, `seal`, `polybag`)
  - *Labeling / Barcode Defect* -> Prep / Receiving (`labeling`, `barcode_verification`)
  - *Weight Discrepancy* -> Pack / Shipping (`scale_check`, `volumetric_weight`, `dws_scan`)
  - *Damage / Inventory Degradation* -> Receiving / Returns (`condition_grade`, `damage_inspection`)
- Implements strict anti-hallucination guardrails and uncertainty detection.

### 2.5 Dossier & Dispute Generator (`recovery_manager/dossier.py`)
- Formats structured assessment results into audit-ready Markdown dossiers.
- Generates platform-specific formal dispute letters tailored for Amazon Seller Support and carrier claims departments.

### 2.6 Evidence Contract Adapter & Interoperability (`recovery_manager/contract.py`)
- Implements the official CUBE Evidence Contract v1.0 standard `handle(request) -> AgentOutput`.
- Ingests upstream `previous_evidence` (Receiving, Prep, Pack, Returns) conforming to standard evidence record schemas.
- Computes canonical SHA-256 `content_hash` over immutable evidence keys.
- Enforces strict multi-tenancy isolation via `org_id` validation.
- Provides native fail-open fault handling: non-blocking pending review outputs on unhandled exceptions.

## 4. Model / Agent Usage & Reasoning Strategy

Unlike simple heuristic matching, the Recovery Manager uses a **structured deterministic reasoning architecture**:

1. **Explicit Operational Evidence Retrieval**:
   - Zero hallucination is guaranteed because claims cannot be formulated without verified references to existing evidence IDs and timestamps.
2. **Defensibility Over Claim Maximization**:
   - In accordance with the critical rule, the engine does not attempt to maximize claims at the expense of defensibility.
   - If an operational record does not cover the specific check in question, the system refuses to guess and yields `SILENT` or `UNCERTAIN`.
3. **Temporal Ordering & Chain of Custody**:
   - Evidence timestamped before carrier dispatch takes precedence over platform inbound claims, establishing that defects occurred while in carrier or warehouse custody.
4. **Natural Language Dispute Synthesis**:
   - For actionable claims, the agent synthesizes formal dispute arguments quoting explicit operational telemetry (e.g. scale calibration records, polybag thickness in mils, barcode scan confirmation).

## 5. Important Engineering Decisions

### 5.1 Deterministic Rules vs. Open-Ended LLMs
- **Decision**: Implemented deterministic operational rule matching with exact citation tracking rather than unconstrained generative prompts.
- **Rationale**: Financial and compliance disputes require 100% reproducibility. Open-ended LLMs risk hallucinating timestamps, photo links, or pass statuses, which could lead to platform penalties or seller account suspension.

### 5.2 Decoupled REST Backend with Lightweight Client
- **Decision**: Developed a FastAPI backend (`server.py`) serving a static, vanilla CSS/JS responsive frontend (`web/`).
- **Rationale**: Avoids bloated JavaScript frameworks while delivering rich aesthetics, instant sub-millisecond scenario switching, and headless scriptability for automated CI/CD pipelines.

### 5.3 Unified Scenario Schema
- **Decision**: Consolidated all 8 canonical test scenarios into a structured JSON database (`data/scenarios/all_scenarios.json`).
- **Rationale**: Allows identical test data to drive both the automated Pytest suite and the interactive Web UI carousel without code duplication.

### 5.4 Multidimensional Indexing in Evidence Store
- **Decision**: Maintained separate hash indices for shipments, orders, SKUs, and units.
- **Rationale**: In real-world ecommerce, fee reports frequently omit shipment IDs (e.g., citing only an order ID or ASIN). Multi-key indexing guarantees evidence discovery across varying data fidelity.

### 5.5 Multi-Tenancy Isolation Enforced at Store & Ingestion
- **Decision**: Every model and query enforces strict `org_id` partition boundaries. Evidence belonging to one organization is never matched or cross-referenced against charges for another organization.
- **Rationale**: Prevents accidental data leakage across client brands and multi-seller accounts. Missing or mismatched tenancy raises an immediate `LookupError`.

### 5.6 Grounding Canonical Findings F-07, F-09, F-10, F-11
- **F-07 (`fulfilment_fee_weight_tier`)**: Yields `SILENT` (insufficient evidence) unless explicit scale/dimension telemetry exists from Pack or Prep stations. Never asserts a weight claim without calibrated proof.
- **F-09 & D-005 ($0.00 Adjustments)**: Non-claimable; marked `SILENT` as $0 claims are commercially meaningless and likely represent data omissions.
- **F-10 (`lost_inbound`)**: Receiving shortfalls are supplier-side issues preceding channel custody. Marked `SILENT` to prevent frivolous platform claims without channel receipt proof.
- **F-11 (`refund_issued_item_not_returned`)**: Disproven (`CONTRADICTED`) when Returns Manager inspection certifies that the correct physical unit was received intact.

### 5.7 Fail-Open Resilience
- **Decision**: Implemented fault-tolerant error wrapping returning standard `pending` AgentOutput envelopes with `agent_exception` codes instead of crashing.
- **Rationale**: A warehouse pipeline must never crash or silently drop financial data due to transient record anomalies.

### 5.8 Full Interoperability: REST API & CLI
- **Decision**: Exposed the contract via `/api/agent/handle` (FastAPI) and `python cli.py handle-request --input <file.json>` (CLI).
- **Rationale**: Enables seamless automated integration into orchestrator workflows while retaining rich browser and terminal visualization.
